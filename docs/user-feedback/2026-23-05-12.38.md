We have progress, but not success on edge cases. 
The tool is rejecting all yellow quality sources, instead of selecting the highest quality version. This is because the program is searching file names for “blank” (which is correct for first pass), and rejects all when that test fails instead of progressing to a second pass that has yet to be defined.
We currently have two excellent edge cases that help define what this behaviour should look like:

    **Peace Be Still**
    Isuue: The PCO link successfully pulls a directory containing songscans, but they don't match the most recent naming conventions, so searching for "blank" returns nothing
    
    **Shout To The Lord**
    Issue: Drive link doesn't lead to a repo. Instead, it leads directly to the document itself. Because there is no other song scan in this file tree, and because there is no directory to search through, the "check for blank tag" step fails and registers no usable song scan, when it should simply use the document as-is

    Desired Solution: Search for title criteria to check for priority quality levels. Run the following tests (written in no particular order)
        1. DePrio key sigs: If a file name contains key signature information (Ab, A, A#, Bb, B, C, etc.), then it is de-preferred. Any document containing none of these is preferred.
        2. Check for Directory: Basically, check to see whether the link leads to a directory or simply straight to the document. If document, then the program checks file-name for prio status. Document being the case *does not* need to affect priority status, other tests are sufficient
    deprioritized documents are not necessarily excluded from selection. UI should allow manual selection when multiple docs have similar priority status.

    Also, UI should have a selectable feature that allows user to manually select any song scan. This only runs on user call, automatic behavior remains the same except where described above, we only want to add a feature that gives the user more options without unnecessarily adding active steps to the default chain

Resulting song scan selection progress chain should default to:

1. Green: Automatically search for and select the green tier song scan with exact criteria matches (correct in current build, do not alter)
2. Yellow: In step 1 fail cases, run tests to search for second choice song scans. If the highest priority category contains only one clear frontrunner, default to that. Otherwise, prompt user to break tie
